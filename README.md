# 低功耗设备仿真系统

这个 Go 模块用纯时间线模型模拟处理器、外设和唤醒事件，不依赖硬件。

## 模型

- 时间单位使用 `time.Duration`，能耗累计单位为纳焦（nJ）。
- 处理器状态为 `active`、`sleep`、`waking`。
- 外设通过名称注册到同一个 `Timeline`，可被任意事件复用。
- 事件按时间排序；同一时刻的多个原因合并为一次恢复和一个并发处理组。
- `SleepUntil` 会拒绝关闭仍有未完成传输的外设。
- 唤醒阶段显式占用 `WakeDuration` 并累计 `WakeEnergyNanos`。
- `SaveSnapshot`/`LoadSnapshot` 使用 JSON 保存完整状态，可恢复后继续调度和演练。
- 电源域通过 `AddDomain` 注册，域有独立的开关和静态功耗；外设用
  `AddPeripheralToDomain` 挂到域里，并可声明 `DependsOn` 唤醒依赖。
- 某个外设传输未结束时，关闭它依赖的电源域（或外设）会被阻断，
  但其他独立域可以照常关闭，不必一起保持活跃。
- 事件触发时会沿依赖链把外设和所属域一起上电，无关域保持关闭。
- `SupplyEnergyPerMillisecond` 表示供能上限（0 为不限）。瞬时功耗超过上限时
  时间被拉长（欠压），能量守恒，拉长的时间计入 `WaitDuration`，
  方便对账工作量、等待与能量。
- 唤醒是分段推进的：快照可以保存在 waking 途中，恢复后接着走完剩余的
  唤醒过程，不会直接跳成已唤醒。
- 进入休眠同样是分段推进的（\`SleepEntryDuration\`）：过渡耗能按实际推进量
  累积，快照可保存在进入途中，恢复后接着走完剩余过程，不退回也不重复计算；
  尚未真正睡着就被紧急工作打断时，唤醒只按进入进度比例支付，不收取完整
  唤醒过程。
- 事件可带 \`Deadline\`：设备按唤醒延迟提前唤醒以赶上时限，处理完成后
  分别记入 \`CompletedOnTime\` 与 \`MissedDeadlines\`，明确哪些请求完成、
  哪些错过时限。
- 带 \`Urgent\` 的事件会打断休眠进入：已消耗的能量不退回，待关机清单被
  丢弃，与事件无关的独立电源域保持关闭，不被无条件唤醒。
- \`SupplyRecoveryAt\` 表示供能恢复时刻：恢复前按 \`SupplyEnergyPerMillisecond\`
  限流拉长，恢复后按 \`RecoveredSupplyEnergyPerMillisecond\`（0 为不限）。

## 核对场景

`main.go` 包含 40ms 周期采样与突发同时到达、70ms 第二次周期采样的场景。
77ms 时的账目为：

- 总时间：77ms
- CPU 工作量：8ms
- 外设传输工作量：14ms
- 活跃：10ms，休眠：63ms，恢复：4ms
- 恢复次数：2，第一次保留两个唤醒原因
- 总能耗：85.3µJ

运行：

```sh
go test ./...
go run .
```

`main.go` 还包含多电源域场景：radio 依赖 analog 域中的 adc，传输途中关闭
analog 域会被阻断（输出 `blocked:` 行），独立的 io 域照常关闭；供能上限
3000nJ/ms 低于活跃功耗，时间被拉长并计入 `wait`。

增加设备类型时，只需创建外设实例或事件类型并挂到同一时间线，不需要改变时间推进、快照和能耗累计逻辑。

## 节能方案研究

`study.go` 支持对同一份到达任务记录分别采用不同入睡等待门槛
（`SleepWaitThreshold`）与唤醒策略（`WakeEager` 提前唤醒 /
`WakeLazy` 到达才唤醒）运行，形成相互独立的 `PlanResult`：

- 比较各方案的实际执行、过渡能耗（唤醒 + 休眠进入，含被打断的进入）、
  未完成任务及截止时间，全部来自已发生的账目，不用计划节能量替代。
- `Study.Run` 的 `inject` 参数表示中途新增的紧急任务：只在到达后
  影响尚未发生的决策；已保存的旧方案结果保留原任务与策略依据。
- `runner.Snapshot`/`restoreRunner` 支持在过渡进行到一半时保存重开，
  恢复运行与连续运行的任务完成和能量账目一致（能量守恒）。
- `Study.Report` 输出对比表；`main.go` 用短间隔密集任务
  （等待门槛更省）和长空闲后紧急任务（提前唤醒赶上截止时间）
  展示策略差异。
